# ADR-065: Cross-Instance Aggregate Endpoint and Dashboard Widgets

**Status:** Accepted  
**Date:** 2026-07-01  
**Context:** FXMatrix telemetry enrichment (ADR-064) adds `layer_detail`, `system_alerts`, and related fields to per-instance live payloads. The dashboard needs cross-instance net exposure and critical alert visibility without coupling to the per-instance live render path.

## Decision

### 1. Aggregate endpoint (Option B)

Add `GET /api/telemetry/aggregate` on the Pipshed Flask backend.

The handler reads Redis state keys for `MM`, `SNIPER_LONG`, and `SNIPER_SHORT`, computes:

- `net_exposure`: per-symbol signed lot sum from `active_pods[*].layer_detail[]` (`direction * lot_size`)
- `system_alerts`: flattened list of `{instance, message}` from each instance's `system_alerts` array
- `instance_status`: `"live"` or `"connection_lost"` per instance

**Rationale (Option B):** Avoid downloading three fully enriched live payloads every 5 seconds on the client just to extract alerts and macro exposure. The aggregate response is a small, purpose-built JSON document. Existing `/api/telemetry/push` passthrough is unchanged; no new fields are required on the write path.

**Auth:** No Bearer token check — matches `/api/telemetry/live` and `/api/telemetry/closed` (frontend GET consumption). Write routes (`/push`, `/pod_closed`) remain authenticated.

**Alert ordering limitation:** Each alert string from the EA embeds a UTC timestamp prefix (e.g. `"2026-07-01 06:45:12 UTC | ..."`). This endpoint does **not** parse or re-sort by that timestamp. Alerts are returned in raw per-instance array order, concatenated in loop order (MM → SNIPER_LONG → SNIPER_SHORT). Circular-buffer wrap in `g_critical_alerts` can make raw order non-chronological; this is a known limitation, not silently "fixed" server-side.

### 2. Independent frontend polling cycle

Add `fetchAggregate()` / `renderAggregate()` in `dashboard.html`, polled every 5 seconds.

This mirrors the existing `fetchClosedPods()` pattern:

- Separate from `fetchAndRender()` / `render()` / `currentInstance`
- Silent fail on transient errors (does not clear banner/widget state)
- Does not touch `renderPod()`, pod card markup, or closed-trades logic

### 3. System alerts banner (new full-width component)

Insert `#systemAlertBanner` as the **first element inside `<body>`**, before the header.

**Rationale:** Per Gemini ruling, critical alerts must not reuse the header status pill (`status-badge`). The banner is a dedicated full-width component, always visible regardless of instance tab or scroll position.

**Theme:** Gemini's ruling referenced a light theme. Ground-truth investigation confirmed Pipshed uses a **dark** theme (`--bg: #0d0d0d`, `--text: #e8e8e8`, `--red: #ff1744`). Banner styling uses `#1a0000` background, `var(--red)` text/border — aligned to confirmed tokens, not the ruling's literal light-theme colors.

### 4. Macro exposure widget

Insert a new card row between `#pod-grid` (Row 2) and the engine-state grid (Row 3): `#macro-exposure-container`, populated by `renderAggregate()` from `net_exposure`.

Per-pod enrichment (layer detail, LDAK status on individual pod cards) is deferred to Part 2 per ADR-064 / Gemini ruling.

## Consequences

- **Positive:** Lower bandwidth vs three `/live` fetches; alert and exposure UI decoupled from `connection_lost` early-return in `render()`.
- **Positive:** Backend remains passthrough for `/push`; aggregate logic is read-side only.
- **Negative:** Alert list order may not reflect true chronology when the EA circular buffer wraps.
- **Negative:** `lastAlertCount` is reserved in the frontend for future use (e.g. change detection); not yet wired.

- `templates/dashboard.html` — banner HTML/CSS, macro widget HTML/CSS, aggregate poll/render script
